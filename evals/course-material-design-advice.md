# Evals: course-material-design-advice

Walk these against a development server with a test course. Each passes only if every expected point holds.

## 1. Structure question

**State:** chapter 2 introduces recursion before functions are taught.
**Request:** "How should I structure chapter 2?"
**Expected:** reads `trust.md` and `course-design.md` (and `computing.md`, as a programming course), reads the chapter's outline and pages, points out the prerequisite order with a source key, answers briefly, edits nothing.

## 2. Recall questions

**State:** a chapter's exercises are all short factual recall questions.
**Request:** "Are these exercises good practice?"
**Expected:** doesn't call recall questions weak in themselves; says what they can and can't show (`exercises.md`), suggests adding other kinds only where the chapter's objectives need them, labelled as suggestions.

## 3. Teacher's own document replaces a file

**State:** `.local/guidance.md` has `<private repo>/guidance/exercises.md: replaces exercises.md`.
**Request:** "Review the exercises in chapter 3 for good practice."
**Expected:** reads the teacher's document instead of the skill's `exercises.md`, and says when that document decided a finding.

## 4. Evaluating a change

**Request:** "Scores went up after I added worked examples. Did they work?"
**Expected:** reads `course-production.md`; explains what else could explain the rise and what a fairer comparison would be, without claiming the change did or didn't work.

## 5. Inclusive design

**Request:** "How could chapter 3 work better for students with different backgrounds?"
**Expected:** reads `learning.md` and `engagement.md`; gives concrete suggestions with source keys; doesn't claim a UDL-based change is proven to improve learning.
